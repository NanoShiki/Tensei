# 项目文档规范

本规范适用于本项目的策划、美术、程序及 AI 代理。项目文档以 `Docs/` 为主要存放位置，围绕模块与功能组织，作为理解和修改项目的共同依据。

## 需求整理与表达

- 开始执行前，先将用户提示词整理为更规范、清晰的表述。可以调整语序、分段和组织结构，并完整保留原始信息、语义、背景、目标、约束、示例、优先级、交付范围和疑问。
- 整理应以信息完整为前提，避免因提炼、压缩或概括造成信息流失。整理后对照原提示词检查内容，保留不确定性和条件关系；存在歧义时明确标注，避免擅自补充结论或改变意图。
- 将用户已确定要求、代理设计建议和待确认问题分别标明，后续补充应同步更新规范化表述与相关文档。
- 文档及协作沟通以直接陈述句为主，严禁使用“不是……而是……”及类似的否定转折句式。
- 美术素材主要由 AI 代理调用生图模型生成，制作约定统一维护在 [美术风格与素材制作](../美术/美术风格与素材制作.md)。

## 文档是完整的整体

- 一个文档应完整表达其主题。同一功能的玩法规则、美术表现、交互反馈和程序实现说明，按需要在同一文档内组织，不按工种拆成彼此割裂的策划案、设计案和技术文档。
- 文档应说明该主题的目标、规则、表现、实现及必要的依赖关系；具体章节按实际需要设置，不强制填充与主题无关的内容。
- 允许只有单一作用但主题完整的文档，例如整个游戏的玩法设计、世界观设计或独立的技术约定。
- 当主题过大时，可以按职责清晰的子模块或独立功能拆分。每份文档仍需完整表达自身主题，并通过链接说明与其他模块的关系，不能仅因策划、美术、程序的分工而拆分。
- 同一规则或事实应有明确的主要维护位置，其他文档通过链接引用，避免复制后产生不一致。

## 全局方向与模块文档分工

- 项目负责人希望亲自维护一至两份全局性文档，负责整体愿景、主游戏与终局玩法的方向及关键取舍；具体是哪一至两份，由项目负责人确定。现有 [整体玩法设计](../游戏整体/整体玩法设计.md)可作为全局方向入口。
- AI 代理负责按模块持续细化和维护眷族、锻造、交易、战斗、存档等具体文档，形成可审阅的规则、示例、状态和待确认问题，提交变更供项目负责人查看效果并反馈。
- 收到新的全局方向后，先更新受影响的模块文档并检查跨模块一致性。若模块设计需要改变全局承诺，应在交付说明中提出具体建议供项目负责人取舍；项目负责人明确要求修改全局文档时，按该要求同步修改。
- 项目负责人审阅后的调整继续回写对应模块的主要维护文档。未确认的实现细节保留为建议，不把代理提案写成已确定规则。

## 按模块组织目录

- 主要文档放在 `Docs/` 下，按模块或主题建立子目录，不将所有文档堆放在 `Docs/` 一级目录。
- 跨模块的项目规范、整体玩法和世界观等内容也应归入对应主题目录。
- 文档归入其主要负责的模块；涉及多个模块时，用相对链接关联其他相关文档。
- `Docs/` 一级目录可以放置必要的总览或导航文档，具体内容放入对应子目录。
- 只创建当前需要的目录，不为尚未开展的模块预建空目录。

以下仅为组织示例，不代表相关模块已经实现：

```text
Docs/
├─ 项目规范/
│  └─ 项目文档规范.md
├─ 游戏整体/
│  ├─ 整体玩法设计.md
│  └─ 世界观设计.md
└─ 战斗系统/
   ├─ 战斗系统说明.md
   └─ 技能系统/
      └─ 技能释放.md
```

## 中文命名与标题

- 文档文件名称和标题必须以中文为主，清楚表达模块、功能或主题；文档目录也优先使用中文。
- 技术术语、代码标识符、命令和路径可以保留原文，必要时与中文说明组合使用。
- 不使用日期、版本号或“最新版”等后缀重复保存同一主题的多个现行版本；持续更新同一份文档。
- 仓库已有的工具或入口约定文件名，例如 `AGENT.md`、`README.md`，可以保留，其正文标题和说明以中文为主。

## 对齐项目当前状态

- 文档应反映当前有效的设计约定和实际实现状态，不能把待实现的设计描述为已有功能。
- 需要保留的规划应明确标记为“待实现”或“待确认”，并与当前已实现内容区分；状态变化时及时更新或移除标记。
- 功能、资源、接口、路径或工作流程发生变化时，在同一次变更中更新相关文档，修正受影响的引用。
- 已废弃或已被替代的说明应直接删除或改写，不在正文中持续堆积旧方案、讨论记录和过时操作步骤。历史追溯使用 Git 提交和 PR 记录。
- 如仍然有效的兼容限制或设计取舍会影响后续工作，应保留必要说明，但不复制完整讨论历史。
- 文档与实际实现不一致时，应先核实当前状态与本次任务目标，再同步修正文档或实现，不应未经核实便以任一方覆盖另一方。

## 实现前必须查阅文档

1. 开始功能实现或修改前，必须先检查 `Docs/` 中是否存在与当前任务相关的文档，按模块、功能名称和关键术语检索。
2. 阅读相关文档及其必要引用，确认当前规则、美术与交互要求、实现状态和模块依赖，再开始实现。
3. 如果没有相关文档，不得假定不存在设计约束；结合当前任务要求与项目现状开展工作。形成需要持续维护的模块或功能说明时，在对应目录新建完整文档。
4. 完成变更时，同步维护受影响文档，清理失效内容，并检查文件名称、标题、目录归属和链接是否符合本规范。

## 项目进展与计划同步

[项目管理与开发计划](../游戏整体/项目管理与开发计划.md)统一维护当前进展、任务优先级、里程碑依赖、待决策项与接手入口。相关设计、实现、素材和验收变化影响项目范围或开发进度时，在同一次变更中同步更新该文档及核对日期；具体规则仍在模块文档维护。设计完成、原型实现、技术验证和用户认可分别记录。更新方式与影响检查表见该文档的持续维护规则。

## 完成检查

- 是否已在实现前查阅相关文档，并落实其中与当前任务有关的有效约定？
- 文档是否围绕完整主题组织，且放在合适的模块子目录？
- 文件名称与标题是否以中文为主？
- 当前实现、待实现设计和待确认事项是否清楚区分？
- 本次变更是否同步更新了说明和引用，并清理过时或重复的信息？
